# 0x0207：240 Hz IMU 更新与 200 Hz 读取负载

根据前文的 IMU 内部更新目标，将加速度、陀螺及 SFLP 从名义 120 Hz 提到
240 Hz。LSM6DSV16X 原始传感器的高精度 ODR 模式另有 200 Hz 档，但当前 SFLP
姿态融合接口的邻近档位是 120/240/480 Hz，因此没有把 240 Hz 标称为精确 200 Hz。
policy 的 50 Hz 时基及 robotd 配置未修改。

## 固件和实物

- 诊断版本 `0x0207`，改动提交 `fc66aa7`。
- CTRL1/CTRL2 读回 `0x07`，SFLP_ODR 读回 `0x63`，保留必需的位 6、1、0。
- 实测新融合数据约 251.35 次/秒，属于本板实际值；240 Hz 是配置名义值。
- 额外 1,000 次 IMU 采样全部成功，四元数均有效；诊断年龄 0–3 ms。
- 静态末段角速度均值 X/Y/Z 约 -0.0003/-0.0045/-0.0645 deg/s。
- MCU 编译及 5/5 宿主测试通过。程序读回一致，末尾 8 KiB 配置页保持原值。
- 只读取舵机寄存器，没有发送扭矩、位置等动作指令。robotd/padd 保持停止。

当前发布的 `firmware-20260916` 仍为 0x0206；0x0207 是本轮本地构建、烧录验证版。

## 测量方法

共享 Dynamixel 总线为 1 Mbps、8N1。先做 Python 探针，再用原生 C 探针复核，
避免将 Python CRC/解释器开销误当成总线上限。C 探针只实现 SYNC_READ，检查
CRC、回复 ID/数量/顺序/长度及设备错误码；不积压多个未完成请求。

“线速占用”按实际收发字节 × 10 bit / 时间 / 1 Mbps 计算，包含状态包及填充，
不包含线路空闲、设备处理和操作系统等待。“事务耗时”另外实测，含等待完整回复。
15 个舵机的 Return Delay Time 寄存器只读检查均为 0，没有改动其 EEPROM。

## 原生 C 结果（240 Hz 固件，各 10 秒）

| 请求方式 | 实际 IMU 读取率 | 实际舵机读取率 | 线速占用 | 结果 |
|---|---:|---:|---:|---|
| 16 设备合并读，目标 50 Hz | 约 50 Hz | 约 50 Hz | 19.93% | 500/500 成功 |
| 只读 IMU，目标 200 Hz | 约 200 Hz | 0 | 7.60% | 2,000/2,000 成功 |
| 合并读 50 Hz + 额外 IMU 150 Hz | 平均约 200 Hz | 约 50 Hz | 25.61% | 2,000/2,000 成功 |
| 16 设备合并读，目标 200 Hz | 约 148 Hz | 约 148 Hz | 58.93% | 回复无错误，但跳过 519 个计划时隙，未达到目标 |

合并事务平均约 6.7–6.8 ms，P99 约 7.0 ms，超过 200 Hz 的 5 ms 周期；单独
IMU 事务平均约 2.67 ms。全设备读取目前无法稳定实现 200 Hz，即使纯字节占用
尚未达到 100%。

120 Hz 固件的对照结果几乎相同：合并读 50 Hz 占 19.93%，IMU 单独读 200 Hz
占 7.61%，混合读占 25.61%；说明内部更新提速本身没有增加 Dynamixel 流量。

## 一分钟混合读取复测

最终读回并执行真实系统复位后，运行合并读 50 Hz + 额外 IMU 150 Hz：

- 12,000 次事务全部成功，未跳过计划时隙。
- 平均 IMU 读取率 200.008 Hz，舵机读取率 50.002 Hz。
- 线速占用 25.609%，事务均值 3.697 ms、P99 6.961 ms、最大 7.916 ms。
- 探针自身 CPU 约 2.07%（一核口径）。
- 诊断版本始终 0x0207，错误码 0，无 FIFO 溢出或看门狗复位标记。

这证明的是**平均 200 Hz 的只读调度能力**。合并事务仍会占据超过 5 ms 的时间，
所以不能将结果说成“每 5 ms 严格均匀地收到一个 IMU 样本”。它也不是现有
robotd 已经实现该调度，或完整 policy/动作写入路径的验收。

## 尚未发送的电机写入：字节预算估算

Protocol 2.0 不含额外填充时：

- 16 设备、每台读 12 字节：请求 30 + 回复 16×23 = 398 字节。
- 单独 IMU：请求 15 + 回复 23 = 38 字节。
- 15 舵机位置 SYNC_WRITE：14 + 15×(1+4) = 89 字节。
- 每秒一次的 15 舵机电压/温度读取：239 字节。

因此，50 Hz 位置写入约增加 4.45% 线速占用，慢传感器读取再增加约 0.239%。
混合读取加上这些常规写入的理想字节预算约 **30.3%**，但本次没有真的发送
位置写入，推理和调度耗时也需另算。混合只读事务的累计服务时间约占观测窗口
74%，与 25.6% 的线上字节占用是两个指标。

若整个读写控制循环都改成 200 Hz，理想字节预算已约 **97.6%**，还没计入额外
填充和间隔；并且与既有 50 Hz policy 时基不一致，不采用这种方案。

## IMU 本地 SPI

按当前名义 6 MHz SPI、1 ms 状态轮询、每次融合产生 quaternion + gbias 两条
FIFO 记录估算，SPI 时钟占用约从 120 Hz 时的 1.03% 升到 240 Hz 时的 1.40%。
这是按源码传输字节推算，不是逻辑分析仪实测，也不包括 CPU 软件开销。

## 证据位置

当前工作区 `artifacts/imu-rate-load-2026-09-17/` 保存只读 Python/C 探针、
120/240 Hz 对照、60 秒复测、返回延时寄存器、Flash 备份/读回及新固件。

当前建议：内部使用 240 Hz，现有 policy/全设备循环继续 50 Hz。若需要更密集的
上位机 IMU 数据，可以另行实现混合读取调度；本轮未改运行时调度或发布 release。
