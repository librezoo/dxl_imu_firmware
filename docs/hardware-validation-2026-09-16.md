# 0x0202 烧录与只读总线验证

2026-09-16，用户接入 WCH-Link 后，在当前复刻机器人上完成本次验证。
这是该板卡的实测记录，不是官方 IMU 板或运动控制验收。

## 烧录与数据保留

- 下载器：WCH-LinkE，固件 v2.18；工具 wlink 0.1.2。
- 确认目标为 CH32V203C8U6（ChipID 0x20300500），Flash 64 KiB，未读保护。
- 烧录前备份完整 64 KiB Flash，并另存 0x0800E000 起的 8 KiB 配置页。
- 最终镜像的源码提交为 `3574f9c`，诊断版本 `0x0202`，BIN 11,420 字节。
- 完整读回确认应用字节与镜像一致，两个配置页与原备份逐字节一致。
- 没有修改舵机寄存器或给电机发送运动指令；robotd/padd 保持停止。

## 实机补充发现：复位后的首包少一个字节

`0x0201` 已能完成 3,000/3,000 次合并读取，但复位后的第一个诊断状态包
仍会只收到 34 字节，线上 Length 要求 35 字节；原 `0x0200` 也有此现象。

发送路径启动 DMA 前未清除 UART 的 TC 标志。根据仓库内 WCH USART 驱动说明，
TC 可显式清除，或者通过读取 STATR 后写 DATAR 的序列清除。首次 DMA 发包
没有保证这个序列，旧 TC 可能让代码过早切回接收方向，截掉最后一个 CRC 字节。

`3574f9c` 在启用 USART/DMA TX 前增加 `USART_ClearFlag(USART3, USART_FLAG_TC)`，
然后仍等待 DMA 完成和 UART 真正发送完成再释放总线。版本增加为 `0x0202`。
三轮复位后的首个诊断请求均完整成功，未用丢弃首包或重试掩盖该问题。

## 0x0202 实测

每次合并请求包含 IMU ID 200 和 15 个舵机，地址 124、长度 12，1 Mbps、50 Hz，
30 ms 超时。成功要求 CRC、16 个回复的数量、顺序、ID、长度及错误码全部正确。

| 运行条件 | 合并请求成功 | 时长 | 首个诊断请求 |
|---|---:|---:|---|
| 烧录后直接运行 | 3,000 / 3,000 | 60 秒 | 成功 |
| 显式系统复位后 | 1,000 / 1,000 | 20 秒 | 成功 |
| 最终 Flash 读回后再系统复位 | 1,000 / 1,000 | 20 秒 | 成功 |

三轮共 5,000 次，约 49.994–50.000 Hz：

- 无 CRC、超时、回复数量、顺序或设备错误；每次只有一份 IMU 回复。
- 5,000 个四元数均满足官方解码接受条件，原始数据持续变化。
- 每轮开始和结束均读到版本 `0x0202`、`last_error=0`。
- 采样计数分别从 145 增至 6165、131 增至 2151、138 增至 2158。
- `reset_reason=2` 为本次软件复位标记，位 0 为 0；没有采样中看门狗复位证据。

普通 Debug 与 UBSan 测试均 4/4 通过。MounRiver GCC 8.2.0 MCU 构建成功，
text=11,372、data=48、bss=4,264 字节；SDK、链接范围和配置页布局未改动。

## 调试器暂停造成的中间失败

完整 Flash 读回会介入调试并暂停 MCU。中间出现过恢复执行后无串口回复；
读取 RX 缓冲区时看到损坏字节。旧镜像与新镜像的 RCC/USART 波特率寄存器相同，
不支持“新固件改错波特率”的推断。重新完成系统复位后恢复正常。

本次工具的 `wlink reset run` 实际走恢复执行路径，不能当作完整系统复位。
最终验证在读回后使用与 WCH `NVIC_SystemReset()` 相同的 PFIC 写操作：

```sh
wlink write-mem 0xe000e048 0xbeef0080
```

这个命令会复位当前连接的 MCU，只适用于已经确认的目标。执行后未再进行
会暂停 MCU 的调试读取，最后一轮串口采样成功。中间失败的日志和旧镜像备份
保留在本地采集目录，未混入上表的最终版本正常运行统计。
